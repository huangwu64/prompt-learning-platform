## 〇、前端初始化项目流程（前端人员进场必读）

> 本节是前端人员**进场第一步**。按顺序执行，即可跑通「代码拉取 → 工程初始化 → 请求层 → 联调登录注册 → 提交」全流程。

### 〇.1 环境准备

| 依赖 | 要求 |
|------|------|
| Node.js | ≥ 18（推荐 20+） |
| Git | 已安装并配置用户（`git config --global user.name / user.email`） |
| 后端服务 | 可启动（见 `project/ai-platform/README.md`，后端端口 8080） |

### 〇.2 获取代码 & 切换分支

### 〇.3 初始化前端工程

```bash

```

### 〇.4 配置 Vite 开发代理（vite.config.ts）

后端已放行 CORS，但更推荐用 Vite 代理转发，请求走同源更干净：

```ts
// vite.config.ts
export default defineConfig({
  plugins: [react()],
  server: {
    port: 5173,
    proxy: {
      '/api': { target: 'http://localhost:8080', changeOrigin: true }
    }
  }
})
```

> 作用：前端 `fetch('/api/...')` 自动转发到后端 8080，无需处理跨域。

### 〇.5 建立统一请求层（src/services/request.ts）

所有接口调用必须走该封装（自动带 token、统一错误处理、401 跳登录）：

```ts
import axios from 'axios'

const request = axios.create({ baseURL: '/api', timeout: 30000 })

request.interceptors.request.use(cfg => {
  const token = localStorage.getItem('token')
  if (token) cfg.headers.Authorization = `Bearer ${token}`
  return cfg
})

request.interceptors.response.use(
  res => res.data,   // 直接拿 {success, data, error}
  err => {
    if (err.response?.status === 401) {
      localStorage.clear()
      location.href = '/login'
    }
    const msg = err.response?.data?.error || '网络异常，请稍后重试'
    // TODO: 接入统一提示组件（如 antd message / 自定义 toast）
    return Promise.reject(new Error(msg))
  }
)

export default request
```

## 二、分支策略

### 2.1 分支模型（精简版 Git Flow）

```
master            稳定主分支（可运行、可演示，禁止直接提交）
  └── develop      开发集成分支（日常合并点，功能完成合到这里）
        └── feature/xxx   功能分支（每人一个，从 develop 切出）
        └── fix/xxx       修复分支（bug 修复）
        └── docs/xxx      文档分支
```

| 分支 | 用途 | 谁可以操作 |
|------|------|-----------|
| `master` | 稳定版本，随时可运行 | 仅合并，不直接提交 |
| `develop` | 开发集成分支 | 全体（经合并） |
| `feature/<模块>` | 新功能开发 | 开发本人 |
| `fix/<问题>` | 修复缺陷 | 开发本人 |
| `docs/<内容>` | 文档变更 | 开发本人 |

### 2.2 分支命名规范

| 类型 | 格式 | 示例 |
|------|------|------|
| 功能 | `feature/<模块或功能>` | `feature/login`、`feature/chat` |
| 修复 | `fix/<问题描述>` | `fix/token-expired` |
| 文档 | `docs/<内容>` | `docs/api-interface` |
| 前端/后端前缀 | 建议加前缀区分 | `feature/frontend/chat`、`feature/backend/chat` |

> 前端功能分支统一用 `feature/frontend/<功能>`，后端用 `feature/backend/<功能>`，一眼区分归属。

## 三、推送与拉取流程

### 3.1 日常拉取（开始工作前必做）

```bash
# 切到 develop 并拉取最新
git checkout develop
git pull
```

### 3.2 配置远程 origin（多人协作时，一次性配置）

当前为本地仓库。多人协作时，由仓库维护者建立一个**共享远程**（本地共享盘 bare 仓库 / 内网 git 服务器），全体执行一次：

```bash
# 后端维护者建立共享远程（示例：局域网共享目录）
git clone --bare "D:\暑期ai学习\版本2" "Z:\shared\ai-platform.git"

# 每位成员（含前端）在自己的工作副本配置 origin
git remote add origin "Z:\shared\ai-platform.git"
git push -u origin develop
git push -u origin master
```

> 若后续改用内网 Git 服务（如 Gitee 私有仓库），只需把 origin 地址换成服务地址，其余流程不变。

### 3.3 开发一个功能（标准流程）

```bash
# 1. 拉取最新 develop
git checkout develop
git pull

# 2. 切出功能分支（前端示例）
git checkout -b feature/frontend/chat

# 3. 开发，随时提交
git add .
git commit -m "feat(chat): 完成对话输入组件"

# 4. 推送到远程（首次加 -u）
git push -u origin feature/frontend/chat
# 之后增量推送
git push
```

### 3.4 功能完成，合并回 develop

```bash
git checkout develop
git pull
git merge feature/frontend/chat
git push
# 合并后删除本地与远程的功能分支
git branch -d feature/frontend/chat
git push origin --delete feature/frontend/chat
```

### 3.5 拉取别人代码

```bash
git pull                # 拉取当前分支的远程更新
git fetch --all         # 获取所有远程分支（含他人新建的功能分支）
```

## 四、提交规范

### 4.1 提交信息格式

```
<type>(<scope>): <描述>
```

| type | 含义 | 示例 |
|------|------|------|
| `feat` | 新功能 | `feat(chat): 实现苏格拉底对话追问` |
| `fix` | 修复 | `fix(auth): 修复 token 过期未跳转` |
| `docs` | 文档 | `docs: 补充接口文档` |
| `style` | 样式/格式 | `style: 统一缩进` |
| `refactor` | 重构（不改功能） | `refactor(works): 抽取模板方法` |
| `test` | 测试 | `test(auth): 增加登录用例` |
| `chore` | 构建/工具 | `chore: 升级依赖版本` |

`scope` 建议用模块名（`auth`、`chat`、`login` 等），没有则省略。

### 4.2 提交纪律

- 一次提交只做一件事，粒度适中。
- 提交信息用中文描述，简洁明确（第一行 ≤ 50 字）。
- **不要提交**：`target/`、`node_modules/`、`.env`、密钥、日志（`.gitignore` 已配置，提交前用 `git status` 检查）。
- 不要提交别人的改动（只 `git add` 自己相关的文件）。

## 五、冲突处理

合并/拉取出现冲突时：

```bash
# 1. 查看冲突文件
git status

# 2. 打开冲突文件，手动保留正确内容
#    <<<<<<< HEAD ... ======= ... >>>>>>> branch

# 3. 解决后标记并提交
git add <已解决的文件>
git commit -m "fix: 解决合并冲突"
git push
```

**红线**：
- 不要用 `git push -f`（force push）覆盖他人提交。
- 冲突解决不了时，保留双方内容让同事确认，不要自行丢弃。
- 操作前不确定就 `git stash` 暂存，不要硬删。
